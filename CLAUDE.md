# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Overview

Relay: a real-time chat with channels and DMs (being built in Phase 3; the client still shows only `#general` until M2). Two independent npm projects, no root `package.json`:

- `server/` — Express 5 + Socket.io 4 + `pg` (PostgreSQL), ESM (`"type": "module"`). Existing code is JS; TypeScript is set up incrementally (`allowJs`, `checkJs: false`, `strict`) so new files can be `.ts`. Do not convert existing JS files.
- `client/` — React 19 + Vite + Tailwind v3 + React Router 7, JSX, with the same incremental TypeScript setup (`noEmit`; typecheck only)

Production (`main`, Phase 1): server on Render and client on Vercel (both deploy `main`), DB on Neon. From the Phase 2 release, Render serves both: Express serves the built client from the API's own origin (topology A), and the Vercel project becomes a redirect.

## Tests (server)

```bash
# needs `docker compose up -d --wait`; run from server/
npm test                                   # vitest run: all integration tests against relay_test
npm run test:watch
npx vitest run test/socket.test.ts         # one file
npx vitest run -t "rejects a duplicate"    # tests whose name matches
```

- Integration tests only (Vitest + Supertest + socket.io-client) against real Postgres; no DB mocking. The client's few unit tests (`client/test/`) run under Node's own test runner (`node --test`, no test library; Node strips the TypeScript types of what they import), for framework-free modules such as `src/lib/reconnect.ts`.
- `server/app.js` exports `createApp({ rateLimits, trustProxy, clientDist })` → `{ app, httpServer, io, stopTimers }` without listening (it does start unref'd timers: the session sweep and the rate limiters' cleanup, all ended by `stopTimers()`); the options default to `RATE_LIMITS` (`lib/limits.ts`), `TRUST_PROXY` and `client/dist`. `index.js` only loads `.env`, checks the DB and listens. Tests start their own instance on port 0 via `startServer(options?)` in `test/helpers.ts`, whose `close()` calls `stopTimers()` and closes `io`. `startServer` defaults to rate limits too high to matter; `test/rateLimits.test.ts` passes the real or low ones, and a new server per test gives fresh counters. `test/spa.test.ts` serves a fixture build (`test/fixtures/client-dist`), so server tests never need a client build.
- **Database guard** (`test/testDatabase.ts`): tests use `DATABASE_URL`, or the local `relay_test` URL if it is unset. The run is refused unless the database name ends in `_test` and the host is local; `vitest.config.ts` checks this before anything runs, `test/setup.ts` re-checks the pool's actual connection string, and the per-test reset (`TRUNCATE` of all V2 tables `RESTART IDENTITY CASCADE`, then re-seeding `#general` with the migration's statement) refuses inside Postgres unless `current_database()` ends in `_test`. The root `.env`'s `DATABASE_URL` (relay_dev) is never used by tests.
- `globalSetup` applies migrations to the test database; `fileParallelism: false` because all files share one database.
- Make requests with `api(server).get/post(...)`, which sends the app's `Origin` like the browser app (a state-changing request without it is refused); send bodies with `.send(object)`, and `.send({})` when there is none (else 415). Use raw `request(server.httpServer)` only to test the Origin checks. `connectSocket(url, cookie?, { origin })` sends the app's `Origin` too unless told otherwise (`null` = none).
- Tests have no cookie jar: `signUp(server)` returns the user and its session `cookie` (`name=value`, from `sessionCookieOf(res)`), which requests send with `.set('Cookie', cookie)` and `connectSocket(url, cookie)` sends in the handshake's headers. Session expiry is tested by moving `expires_at` / `last_seen_at` in the database (`setSessionAgo`), never by waiting; tests call `sweepSessions(io)` directly, and only the timer test fakes `setInterval`.
- Socket tests wait for events (`nextEvent`) registered before the triggering emit — no sleeps/timeouts.
- `test/schema.test.ts` tests every `0002`–`0004` constraint directly in the database, with a factory per table. `test/sessions.test.ts` covers the session cookie, `/me`, expiry, the idle timeout and logout; `test/sessionLifecycle.test.ts` covers sockets: logout disconnecting its session's sockets, and the sweep. `test/security.test.ts` covers the CSRF checks and helmet's headers; `test/rateLimits.test.ts` the login, signup, user search and channel creation limits and `trust proxy`. `test/ordering.test.ts` proves the send transaction's guarantees (concurrent sends are gapless per conversation, a failed send takes no `seq`). `test/conversations.test.ts`, `channels.test.ts`, `dms.test.ts` and `messages.test.ts` cover the conversation REST API (every route's 401, the 404 for non-members, the DM race, pagination edges, read positions); `test/rooms.test.ts` covers socket rooms: members only receive a conversation's messages and typing, and joining, leaving, new DMs and added members move sockets at once. Helpers: `generalId()`, `createChannel(server, user, body)`, `postMessages(conversationId, authorId, count)` (stores messages as the send transaction numbers them, without a socket), `signUp(server, { username })`, `api(server).put`. "Receives nothing" is proven with a later sentinel message: a socket gets events in the order they were sent.

## Environment

- Server env lives in a `.env` at the **repo root**, not in `server/`. `server/config/env.ts` is the **only** module that loads it and reads `process.env`: it resolves the path relative to its own location (with an extra `..` when running from the compiled `server/dist/`), validates everything with zod, and exports a frozen `config` (`config.nodeEnv`, `config.port`, `config.clientUrl`, `config.database`, …). Other code imports `config` — never read `process.env` directly. Invalid/missing variables make the server print their names (never values) and exit 1 before listening.
- Because `config/env.ts` is TypeScript, the server must run via `tsx` (`npm run dev`) or the compiled build (`npm start`); plain `node index.js` no longer works.
- Server vars: `DATABASE_URL` (takes precedence; TLS as its `sslmode` says) or the legacy `DB_USER`, `DB_HOST`, `DB_NAME`, `DB_PASSWORD`, `DB_PORT` (migrations only read `DATABASE_URL`), plus `PORT` (default 5001), `CLIENT_URL` (the app's public URL: default `http://localhost:5173`, where Vite serves the page in development; the Render URL in production; its origin is the only one the Origin checks accept), `NODE_ENV` (`production` on Render makes the session cookie `__Host-relay_session` with `Secure`; leave it unset locally) and `TRUST_PROXY` (how many proxies' `X-Forwarded-For` Express believes for `req.ip`; default 0, trust none; Render needs 1, verified at the release). There is no `JWT_SECRET` any more.
- The client has no configuration: Axios and Socket.io always use the page's own origin (Vite's proxy in development, Express in production). `VITE_API_URL` is no longer read; with no CORS, an API on another origin could not work anyway.
- Local dev uses `DATABASE_URL=postgres://relay:relay@localhost:5433/relay_dev?sslmode=disable` (see `.env.example`). TLS comes from the URL's `sslmode` alone (`connection.js` sets no `ssl` option): `config/env.ts` refuses to start unless a `DATABASE_URL` whose host is not local says `sslmode=verify-full`, which checks the certificate and host name; local hosts use `sslmode=disable`. Docker publishes Postgres on host port **5433** (not 5432) to avoid clashing with a local Postgres install. Never point the running app at `relay_test`; it is reserved for tests.
- Schema is managed by node-pg-migrate SQL migrations in `server/migrations/` (`-- Up Migration` / `-- Down Migration` sections; applied names tracked in the `pgmigrations` table). `0001_initial` is the Phase 0 schema. `0002_v2_schema` drops it and creates the V2 schema (`docs/v2-design.md` §4) with named constraints: `users` (lowercase `username`, `email`; `display_name`; `password_hash`), `conversations` (channels and DMs; the per-conversation `last_seq` counter), `direct_conversations`, `conversation_members` (`role`, `last_read_seq`) and `messages` (`seq`, `author_id`, `client_id`). It seeds the public `#general` channel; its down migration restores the Phase 0 tables. `0003_sessions` adds `sessions` (`token_hash` = SHA-256 of the cookie token, `user_id` ON DELETE CASCADE, `last_seen_at`, `expires_at`, `user_agent`). `0004_public-channel-names` makes channel names unique among public channels only (`conversations_public_channel_name_key`), so a 409 never reveals a private channel; private channels may share names, so `#general` is found by name **and** `visibility = 'public'`. Limits shared by code and tests live in `server/lib/limits.ts`; migrations repeat the ones the database enforces, and `test/schema.test.ts` checks that both agree.

## Architecture

**Auth is server-side sessions in an httpOnly cookie** (`docs/v2-design.md` §6, D3). Signup and login (`server/routes/auth.js`) each create a new session (a cookie the request already carries is never reused): a random 32-byte token goes only into the cookie, and `sessions` stores its SHA-256. Signup creates it in the same transaction as the user and the `#general` membership. `server/lib/sessions.ts` owns the token, the hash and the cookie (`sessionCookie.set/clear/read`): `relay_session`, `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age` 30 days, and in production `__Host-relay_session` with `Secure`. A session is valid until `expires_at` (30 days) and while `last_seen_at` is within 7 days; `findSessionUser` (`server/repositories/sessions.ts`) checks both and moves `last_seen_at` at most once an hour, in one statement. The limits are in `lib/limits.ts`. The session is checked in two places, which must stay in step: `server/http/requireSession.ts` for HTTP (sets `req.user` = `{ id, username, email }` and `req.session`; every failure is 401 `UNAUTHENTICATED` "Your session has expired. Please log in again.") and the `io.use` middleware in `server/socket/socketHandler.js` for the socket handshake, which reads the cookie from `socket.handshake.headers.cookie` and sets `socket.user` (`{ id, username }`) and `socket.sessionHash`. Its rejections say "Authentication error: …", which the client treats as a logout, so a failed lookup says "Server error" instead (and a failed HTTP lookup is a 500). `GET /api/auth/me` returns the user; `POST /api/auth/logout` deletes this session only, clears the cookie and always answers 204. The token must never reach a response body, the logs or the database.

**Sessions and sockets:** on connect, each socket joins its session's room, `session:<token hash, hex>` (`sessionRoom()` in `lib/sessions.ts`). Logout deletes the row, then `io.in(sessionRoom(hash)).disconnectSockets(true)` cuts off every tab of that session (the client sees `io server disconnect` and does not reconnect); the user's other sessions keep their sockets. `routes/auth.js` is therefore a factory, `authRoutes(io, rateLimiters)`, and `createApp` creates the HTTP server and `io` before mounting routes. `sweepSessions(io)` (`server/socket/sessionSweep.ts`) runs every 5 minutes (`SESSION_SWEEP_INTERVAL_MS`): one query (`findValidSessions`) checks every connected session, found through the session rooms, and moves the valid ones' `last_seen_at` (an open socket counts as use); the others' sockets are disconnected; then expired and idle rows are deleted. A failed run is logged, and runs never overlap.

**CSRF** (`server/http/csrf.ts`, three layers with the `SameSite=Lax` cookie): every `POST`/`PUT`/`PATCH`/`DELETE` under `/api` must carry `Origin` equal to `allowedOrigin` (`new URL(CLIENT_URL).origin`), else 403 `FORBIDDEN`, a missing `Origin` included; then `Content-Type: application/json`, else 415 `UNSUPPORTED_MEDIA_TYPE` (so the client sends `{}` when it has no body). Both run before `express.json()`; `GET` needs no `Origin`. Socket.io's `allowRequest` (`allowSocketHandshake`) refuses a handshake from any other origin, or none, before the session is looked up, and logs a warning; CORS does not protect WebSockets. Server and client use the WebSocket transport only: browsers always send `Origin` on a WebSocket handshake, but not on a same-origin HTTP long-polling GET, which the check would refuse. There is no CORS at all (no `cors` middleware or Socket.io `cors` option): the client is same-origin, so no other site may read a response. `helmet` (without its CSP, which belongs to the SPA in Phase 8) adds security headers to every Express response and removes `X-Powered-By`; Socket.io's own responses bypass Express.

**Passwords and brute force:** a new password (signup only) is 8+ characters (code points) and at most 72 UTF-8 bytes, bcrypt's limit, and is rejected rather than cut (`newPassword` in `http/schemas.ts`); login accepts any non-empty password, so older accounts keep working. Login runs one `bcrypt.compare` even for an unknown email, against a dummy hash of the same cost made at startup, so its timing does not reveal which emails exist. `server/http/rateLimits.ts` (`express-rate-limit`, in-memory stores; enough for one instance) limits failed logins per IP and normalized email (successful ones do not count; once limited, even the right password gets 429), signup attempts per IP, user searches (`GET /api/users`) per user and IP, so visitors sharing the demo account do not share a budget, and channel creations per user (only successful ones count); the numbers are `RATE_LIMITS` in `lib/limits.ts`. Over a limit: 429 `RATE_LIMITED` with `Retry-After`. The limiters run before validation, so invalid attempts count, and key on `req.ip`, which depends on `trust proxy` (`TRUST_PROXY`).

**Client auth state** lives in `client/src/context/AuthProvider.jsx`: `{ status: 'loading' | 'authenticated' | 'guest', user, login(user), logout() }`. JavaScript cannot read the cookie, so on start it asks `GET /api/auth/me`, and `ProtectedRoute` / `GuestRoute` render nothing while `loading`. `login(user)` takes the user from the signup or login response; `logout()` calls `POST /api/auth/logout` (with `{}`: the server wants JSON), then becomes `guest`, and the routes redirect. A response interceptor it registers on the Axios instance turns any 401 `UNAUTHENTICATED` into a local logout (a wrong password, 401 `INVALID_CREDENTIALS`, is left to the form). Axios and the Socket.io client are same-origin, so the browser sends the cookie by itself; nothing auth-related is in `localStorage` (the provider deletes the old `relay_token` / `relay_user` keys).

**Data access:** SQL lives in `server/repositories/` (TypeScript: `users`, `conversations`, `messages`, `sessions`). Each function takes a `Queryable`: the pool, or the client inside `withTransaction(fn)` (`server/db/transaction.ts`: BEGIN, COMMIT, or ROLLBACK and rethrow). Emit socket events only after the transaction has committed, and move rooms right after COMMIT with no await in between (read what the events need inside the transaction). There is no service or policy layer (Phase 3 plan §3): routes call repositories, and the only rule is membership. Request bodies and query strings are validated with zod schemas in `server/http/schemas.ts`: `schema.safeParse(req.body)` (or `req.query`), then `next(validationError(result.error))` on failure (400 `VALIDATION_ERROR`, `details` = `[{ field, message }]`). Signup normalizes usernames and emails to lowercase and stores the typed username as `display_name`.

**Conversations** (Phase 3 M1, `docs/phase-3-implementation-plan.md` §5): channels (public or private) and DMs in one `conversations` table. `#general` (`GENERAL_CHANNEL`, looked up by name, never a hard-coded id) is joined by everyone at signup and cannot be left. Routes (TypeScript, each a factory taking `io`, all behind `requireSession`): `server/routes/conversations.ts` (`GET /api/conversations`: my conversations as summaries, most recently active first; `GET …/:id/messages?before=&limit=`; `PUT …/:id/read {seq}`; `POST …/:id/join`, `…/leave`, `…/members {username}`), `routes/channels.ts` (`GET /api/channels?q=`: public channels by name prefix, with `isMember`; `POST /api/channels {name, topic?, visibility?}`: 201, 409 for a taken name), `routes/dms.ts` (`POST /api/dms {userId}`: 201 created or 200 existing; concurrent requests create one DM through `INSERT … ON CONFLICT DO NOTHING` on the pair, the loser rolling back its conversation row) and `routes/users.ts` (`GET /api/users?q=`: up to 10 other users by username prefix, rate limited). Reading needs membership (D14): `http/requireMember.ts` parses `:id` (`parseId`, `lib/ids.ts`: a positive int4, so a huge id is a 404 and not a Postgres error) and answers 404 "Conversation not found." to non-members and for missing or malformed ids alike, so a private conversation's existence never leaks. Join works only on public channels (idempotent; 404 otherwise). Leave works on public channels other than `#general` and on private channels for everyone but their owner (there is no ownership transfer); DMs cannot be left (all 403); leaving removes access at once (the membership row, then `leftConversation`). Only a private channel's owner adds members (403). A new member's `last_read_seq` starts at the conversation's `last_seq`. The summary (`ConversationSummary`, `repositories/conversations.ts`) is `{ id, type, visibility, name, topic, role, lastSeq, lastReadSeq, unreadCount, lastMessageAt, lastActivityAt }`: a DM is named after the other user, `unreadCount = lastSeq − lastReadSeq`, and `lastActivityAt` (the sort key) is the latest message or my join, whichever is later. `markRead` never moves back (`GREATEST`) nor past `last_seq` (`LEAST`). Search prefixes use `starts_with()`, not `LIKE`, and only accept `[a-z0-9_-]`. A path that is not valid percent-encoding is a 400 `BAD_REQUEST` (`errorHandler.ts`).

**Message flow:** history is fetched over REST (`GET /api/conversations/:id/messages`: the latest `limit` (default 50, at most 100) messages, or those before seq `before`, returned oldest→newest; older ones exist while the first has `seq > 1`); live messages arrive over the socket. The client emits `new_message { conversationId, content }`: the server ignores a payload without a valid `conversationId` or non-blank text and rejects over 4000 characters (`MESSAGE_MAX_LENGTH`, counted in code points) with `error`. Then, in one transaction, it takes the next `seq` (`UPDATE conversations SET last_seq = last_seq + 1 … RETURNING`, which locks the row, so seqs are gapless and in commit order per conversation; no row means no such conversation), inserts the message with a server-generated `client_id` only if the sender is a member (`INSERT … SELECT … WHERE EXISTS`; otherwise it rolls back, which returns the seq, and emits `error` "You are not a member of this conversation.", the same for a missing conversation), and moves the sender's `last_read_seq` forward. After COMMIT it emits `message` to the conversation's room only, the sender included (no optimistic UI — the sender renders its own message from the broadcast). REST and socket payloads both use the camelCase shape `{ id, conversationId, seq, userId, username, content, createdAt }`, built for both by `server/repositories/messages.ts`.

**Rooms** (`server/socket/rooms.ts`): every socket is in `session:<hash>`, `user:<id>` and `conv:<id>` for each of its user's conversations. The handshake middleware looks up the memberships (one query; a failure is "Server error: could not load your conversations"), and the connection handler joins all the rooms synchronously, in the tick in which Socket.io registers the socket, so no broadcast misses it. Membership changes call `joinedConversation(io, userId, summary)` (every socket of the user joins the room, and all their tabs get `conversation:joined`) or `leftConversation` (`socketsLeave`, `conversation:left { conversationId }`) right after COMMIT. `socketsJoin` cannot reach a socket that is still connecting, so these also bump `membershipChangeCount()`; a socket whose count changed during its handshake looks its memberships up again once connected (joining and leaving rooms to match), and again while the count keeps changing during that lookup, so a stale result never undoes a leave.

**REST errors** always use the envelope `{ error: { code, message, details? } }`. Routes and middleware never write error JSON themselves: they call `next(new AppError(status, ErrorCode.X, message))` (`server/lib/errors.ts`; use `next`, not `throw`, inside a route's `try` so its `catch` doesn't turn it into a 500). `app.js` mounts `http/notFound.ts` on `/api` after all routes (JSON 404) and `http/errorHandler.ts` last (AppError → its status; bad JSON → 400 `INVALID_JSON`; other body errors keep their 4xx; anything else → logged + generic 500, never a stack). Add new codes to `ErrorCode` only when a response needs one. The client reads messages with `getErrorMessage(err, fallback)` from `client/src/lib/errors.ts`. Socket errors are separate and unchanged (`connect_error` / `error { message }`).

**Logging:** never use `console.*` in server code — import `logger` from `server/lib/logger.ts` (pino, JSON lines on stdout, level from `LOG_LEVEL`, default `info`). Log errors as `logger.error({ err }, 'message')` so the stack is kept, and put context in fields rather than in the message string. `app.js` mounts `pino-http` first (with `httpLoggerOptions`, which add `ip`: `req.ip` as the rate limits see it, to check `TRUST_PROXY`), so every Express request gets one `request completed` line (Socket.io traffic bypasses it); socket handlers use a per-connection child logger. Redaction (`loggerOptions.redact`) hides `req.headers.authorization`, `req.headers.cookie` and `res.headers["set-cookie"]` (both carry the session token), any `password` up to two levels deep, and Postgres `err.detail` (it can contain row values); never log request bodies or tokens. Tests run with `LOG_LEVEL=silent`; `test/logger.test.ts` checks the redaction. The only log line written without `logger` is the config-failure line in `config/env.ts` (a default pino instance, because the logger's level comes from that config).

**Lifecycle:** `db/connection.js` registers `pool.on('error')`: an idle connection dropped by the database is logged and the pool reconnects — without that listener Node would crash (pg-pool emits `error` on the pool). On SIGTERM/SIGINT, `index.js` shuts down gracefully: `await stopTimers()` (clears the rate limiters' cleanup timers and the sweep's, waiting for a sweep in progress), then `await io.close()` (disconnects sockets, which then auto-reconnect to the next instance; closes the HTTP server and waits for in-flight requests), then `await pool.end()`, then exit 0. A 10 s unref'd timer forces exit 1 if that hangs, and repeated signals during shutdown are ignored (Ctrl-C delivers SIGINT from both the terminal and `tsx watch`). Keep anything that holds resources (timers, connections) closable by this sequence.

**Socket events:**
- client → server: `new_message { conversationId, content }`, `typing { conversationId }`
- server → client: `message` (to the conversation's room), `conversation:joined` (a summary) / `conversation:left { conversationId }` (to the user's room), `online_count` (global, from `io.sockets.sockets.size`), `user_typing` / `user_stop_typing` (`{ conversationId, username }`), `error { message }`

Typing is debounced server-side, per socket and conversation: `user_typing` goes out once per burst and `user_stop_typing` after 3s of silence or on disconnect, to the conversation's room except the typist's own sockets. A `typing` for a conversation the socket's rooms do not include (not a member) is ignored.

**Socket lifecycle:** `client/src/socket.js` is a singleton with `autoConnect: false` and `transports: ['websocket']`. `client/src/pages/Chat.jsx` calls `socket.connect()` on mount, registers listeners, and `off`s them + disconnects on unmount; a `connect_error` whose message contains "authentication" (an expired or revoked session) logs the user out. Any other `connect_error` after which the socket is not `active` (the server refused the handshake with "Server error…", and Socket.io gives such a socket up) is retried by `createHandshakeRetry` (`client/src/lib/reconnect.ts`: 1 s doubling to 30 s, ±25 % jitter; reset on `connect`, stopped on unmount), so the tab comes back without a reload. After a lost connection Socket.io reconnects by itself. A `disconnect` with reason `io server disconnect` (the session ended: a logout in another tab, or the sweep; Socket.io does not reconnect after it) asks `GET /api/auth/me`: a 401 logs out through the interceptor, a valid session reconnects. Add new listeners inside that same effect and remove them in its cleanup. Until M2, `Chat.jsx` finds `#general` in `GET /api/conversations`, loads its history, sends with its `conversationId`, and ignores other conversations' `message` and typing events; the composer stays disabled until `#general` is known.

**Routing** (`client/src/App.jsx`): `/` Landing, `/login` and `/signup` wrapped in `GuestRoute` (redirects authed users to `/chat`), `/chat` wrapped in `ProtectedRoute` (redirects to `/login`). These routes exist only in the client (`BrowserRouter`), so every page GET must return `index.html`. On `phase-2`, `server/http/spa.ts` does that when `client/dist` exists: `/assets/*` (hashed) with a year's immutable cache, a missing asset 404, other build files as they are, and `index.html` with `no-cache` for every other GET outside `/api` and `/socket.io`. Vite's dev server does this by itself. `client/vercel.json` on `phase-2` redirects every path of the old Vercel project to the same path on Render (temporary 307); on `main`, until the release, it still rewrites client routes to `index.html` for the Phase 1 client.
